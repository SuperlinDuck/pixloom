# Pixloom Cloud v2：共享资源池与按需环境

日期：2026-10-25。状态：共享池核心已实现；当前配置、验收与实际边界见 [共享池运行说明](cloud-shared.md)。本文保留完整设计目标，自动切换恢复绑定、跨池身份迁移和隔离函数等部分仍属后续工作。[v1](cloud.md) 作为独立适配器保留兼容。

## 决策

默认 Cloud 使用平台预先配置的共享资源池。每个应用在池中分配独立的命名空间、访问权限和配额，不调用 Supabase 项目创建 API。开发环境按需启用，生产命名空间在首次发布时才创建。

首个适配器采用 Supabase 共享池：平台最多配置两个已有项目，分别作为开发池和生产池，多个应用共享池的计算与存储。两个免费项目可以服务多个轻量应用；实际容量取决于总用量，不能承诺固定应用数量。纯静态应用不分配后端命名空间。

这借鉴 Atoms 的平台代管资源、应用环境独立、Agent 操作结构化后端能力的产品思路。Atoms 官方描述了共享基础设施和 Serverless 数据库，但没有公开足以复刻其实现的全部细节；本设计不声称采用其底层供应商或商业协议。

自有 Supabase 保留为独立适配器。已有 v1 绑定继续使用原资源，新共享模式不自动接管、删除或合并已有数据库。

## 资源数量与成本

| 场景                  | 当前 v1            | v2 默认共享池                          |
| --------------------- | ------------------ | -------------------------------------- |
| 创建纯静态应用        | 不创建项目         | 不分配后端                             |
| 第一次需要数据库/登录 | 每应用准备两个项目 | 在已配置开发池创建应用命名空间         |
| 首次发布              | 已提前分配生产项目 | 在已配置生产池创建应用命名空间         |
| 10 个已发布应用       | 最多 20 个独立项目 | 一组两个池项目，包含 20 个环境命名空间 |
| 扩容                  | 随应用数量增加项目 | 按池实际用量扩容或增加池               |
| 高负载或独立配置需求  | 默认独占           | 显式迁移到专属资源或自有 Supabase      |

Supabase 当前 Free 提供两个活跃项目、每项目 500 MB 数据库，闲置一周会暂停。项目数量与应用数量没有一一对应的技术要求。数据库、Auth、文件、流量、邮件和函数等各有独立限制，额度口径以服务商计费页为准，不能简单将两个项目的所有额度都乘二。

容量规划按每个池分别计算：`应用可用空间 = 池容量 - 平台/Auth/索引等开销 - 安全余量`。例如假设生产池实际可分配预算为 300 MB，每个应用预算为 10 MB，最多可预留 30 份空间预算；这只是算术示例，不能证明能承受 30 个应用的请求、并发和文件用量。

平台成本由池计算、数据库/文件存储、出站流量、网关、邮件和备份组成。免费额度可降低试验阶段的服务商账单，网关服务器和运维仍有成本。生产是否使用 Free 由可用性要求决定；不通过伪造活跃请求规避暂停。应用逻辑停用不会让共享 Supabase 项目按应用缩减计算费，也不宣称该适配器具备真正的 scale-to-zero。

## 架构

```text
工作台 / Engineer
    → 控制 API → SQLite（项目、源码、任务、绑定、发布记录）
    → 资源调度 Worker → Cloud Provider 适配器
                           ├─ Shared Supabase：在池内分配命名空间
                           ├─ Legacy Supabase：保留 v1 绑定
                           └─ External Supabase：用户自有资源

生成应用 / 预览
    → Cloud Runtime Gateway（独立于工作台管理 API）
       → 身份与应用授权 → 配额 → 受限数据操作
          ├─ 开发池：应用 A schema / 应用 B schema / …
          └─ 生产池：应用 A schema / 应用 B schema / …
```

控制面继续沿用本机单 Worker、任务 attempt 和提交基线检查；不因加入共享池就宣称平台已支持公开多用户 SaaS。发布网关只需增加 Cloud runtime 的受限路由，工作台、项目管理、DDL 和凭证接口继续保持私有。对外提供业务 API 前必须部署 TLS、限流和应用授权边界。

## 应用与环境隔离

每个应用环境对应平台生成的独立 PostgreSQL schema 和运行角色。开发池与生产池使用不同 Supabase 项目，避免测试请求接触生产数据。应用 schema 不加入 Supabase exposed schemas，不授予 `PUBLIC`、`anon`、`authenticated` 访问权。浏览器经 Gateway 使用逻辑表名，不直接持有池数据库凭证或共享 Supabase 用户令牌。

Gateway 从可信绑定定位 `(installationId, appId, environmentId, bindingGeneration)`，检查会话范围与表定义，再执行参数化、有限操作。客户端传来的 schema、角色、`owner_id` 和环境不能直接作为数据库授权依据。表和列标识符由受校验的结构化定义映射，禁止任意 SQL、任意 PostgREST 过滤器和任意上游 URL。

数据连接按环境、按应用凭证隔离并限制总连接数；运行角色不是 owner，不具备 DDL、`BYPASSRLS`、其他应用角色的成员资格或其他 schema 权限。DDL 使用独立 Worker 凭证。每请求显式事务内设置可信用户上下文，启用并强制执行 owner RLS，提交或回滚后清除上下文，避免连接复用串用户。共享池的私有身份/成员表不得授权给应用角色。

schema 解决命名与权限划分，RLS 解决同一应用内的用户数据权限；两者都不能隔离数据库 CPU、锁、故障与系统级目录可见性。共享池首版只接受平台编译的 CRUD 和迁移，禁止用户数据库连接、扩展、任意 SQL 与管理员凭证。独立计算、强合规隔离或数据库管理员访问需求转到专属资源。

## 身份、存储和函数

### 应用用户身份

首版复用每个池的一套 Supabase Auth 作为身份提供方，并在池内私有控制 schema 保存应用成员关系。同一环境池里的应用共享身份提供方的账号/密码命名空间，但成员、授权和应用数据分别管理。它与登录 Pixloom 工作台的 Google 账号体系相互独立。登录界面文案由应用自行设计。

注册、邮箱验证、密码重置、登录和刷新通过 Gateway 的受限身份适配器完成，不自行实现密码哈希。已有同邮箱身份需登录证明后才能加入新应用，不能仅凭提交邮箱或复用其他应用 token 创建成员关系；重复邮箱和不存在账号采用通用响应，避免泄露其他应用注册信息。回调先落在平台固定端点，再校验 state 并转到登记过的应用地址。

Gateway 验证上游身份后签发仅绑定当前应用与环境的短期会话；上游访问/刷新令牌仅加密保存在服务端，刷新和退出遵守到期、撤销规则。浏览器初期使用内存中的应用会话；刷新需重新登录时如实提示，数据库记录仍持久保存。不依赖预览 opaque-origin 下的 Cookie 或 localStorage 必然可用。

应用注销仅撤销本应用会话及成员数据，不能删除其他应用共享的上游身份。上游账号删除是独立身份生命周期流程。需要独立账号体系、独立邮件模板或独立 OAuth 配置的应用，首版使用自有/专属后端；不能把共享池包装成每应用独立 Auth。

### 文件存储

池使用平台私有存储桶，实际对象键由 Gateway 生成并包含完整应用、环境、用户作用域。Gateway 校验路径、所有权、文件大小和配额后才上传/下载。平台服务凭证若绕过存储 RLS，必须由 Gateway 承担全部授权且禁止任意对象键透传。签名下载链接是短期持有者凭据，限制有效期；桶始终私有。应用删除只清理自身对象和元数据。

### 服务端函数

当前 v1 函数包装器只验证 Supabase 用户，函数名按源码 hash 命名，不能直接搬入共享池。共享项目中的环境变量和服务凭证也不能交给任意生成代码。

共享池第一阶段仅提供平台维护的身份、CRUD、文件操作。请求自定义函数时明确返回“共享池暂不支持此能力”，由用户选择自有后端；Agent 不得静默替换成浏览器逻辑或内存实现。后续函数运行在独立受限执行环境，只有短期、绑定应用/环境/用户及操作范围的 Gateway capability，没有池密钥、数据库连接或工作台令牌；出站、资源和执行时长另行受限。未完成该隔离前，不开放共享池任意函数执行。

## 环境生命周期与发布

| 操作           | 目标行为                                                             |
| -------------- | -------------------------------------------------------------------- |
| 创建应用       | 仅保存控制状态和源码                                                 |
| `cloud_enable` | 校验能力与配额，在开发池分配命名空间；不创建生产环境                 |
| 构建与行为测试 | 只修改本应用开发环境；测试账号和数据按任务标记清理                   |
| 首次发布       | 校验生产池已配置，分配生产命名空间，应用受控迁移，验证后切换发布指针 |
| 后续发布       | 校验环境与兼容迁移，发布结构和函数版本；业务数据原地保留             |
| 失败/取消      | 原线上指针不变；已分配资源记账，异步清理可追踪                       |
| 回滚           | 回退应用代码和兼容的功能映射；不回退业务数据或假装撤销迁移           |
| 下线           | 停止应用公开入口，保留数据，按保留策略处理                           |
| 删除后端       | 显示应用、环境、数据清单并显式确认；绝不删除整个共享项目             |

发布先解析所发布版本的结构化后端定义，再做添加式迁移；禁止自动删列、改变已有列类型和放宽访问权限。迁移成功后若发布失败，新增结构可能已存在，后续重试须幂等且旧代码仍可运行。测试数据、开发身份、会话与 secrets 不复制到生产。

首版每应用只有一个可变开发环境，不承诺每次对话或每个版本有独立数据库。历史预览绑定原环境，不等于历史数据快照。需要分支预览时后续按 schema-only 建临时环境，设置 TTL，只清理测试资源；不自动复制生产个人数据。

## 新数据模型与协议

以下为设计模型。当前实现新增版本化表并保留 v1 表与旧产物路径；会话保存在平台 SQLite，实际表字段及运维行为以代码和运行说明为准：

| 对象                    | 核心字段与约束                                                                                       |
| ----------------------- | ---------------------------------------------------------------------------------------------------- |
| `cloud_pools`           | 安装、提供方、环境、区域、远程项目标识、状态、凭证引用、容量和配额；远程标识在池级唯一               |
| `cloud_apps_v2`         | 项目归属、模式、适配器版本、绑定代次；新共享模式与已有 v1 绑定明确区分                               |
| `cloud_environments_v2` | 应用、环境、poolId、schema、角色凭证引用、状态、结构 hash；`(appId, environment)` 和池内 schema 唯一 |
| `cloud_operations_v2`   | 幂等键、作用域、目标配置 hash、attempt、租约/代次、远端状态、错误与清理状态                          |
| `cloud_deployments_v2`  | 环境 ID、资源类型、逻辑名、内容 hash；禁止只以 pool ref 和 `app` 为唯一键                            |
| 池内私有控制表          | 成员、会话、文件所有权、配额预留与用量；始终带应用和环境归属                                         |

保留 `cloud_enable`、`cloud_schema`、`cloud_test_account` 以及应用侧 `cloud.select/insert/update/remove` 等能力名称，底层改走 Provider 接口：`capabilities`、`ensureEnvironment`、`applySchema`、`inspectSchema`、`usage`、`exportEnvironment`、`deleteEnvironment`。默认操作目标为开发环境，生产迁移仅由发布路径执行。

定义 `pixloom-cloud-v2` 产物协议，只包含应用 ID、当前环境 ID、Gateway HTTPS 端点、绑定代次和逻辑能力清单。开发产物不必包含尚不存在的生产环境配置；发布从指定版本生成生产描述符，不能简单改 `environment` 字段。公开 ID 和配置不作为鉴权凭据，历史版本不能通过修改 JSON 得到其他环境的数据权限。

Gateway 的 `/cloud/v2/apps/:id/environments/:env/...` 仅提供有限身份、表操作、文件接口；管理员 DDL/池配置不在公共路由。预览网络规则仅允许指定 Gateway 的 Cloud 路径，不能因此放行同源工作台 API。OPAQUE Origin 的预览按应用短期凭据鉴权，不能依赖 CORS 单独隔离。

## 配额、恢复与容量

每池统计数据库和索引容量、存储、流量、Auth/邮件、连接与延迟；每应用另有表数、行/字节、文件、请求速率及并发预算。操作前预留配额，完成后核销；并发写入的额度检查必须和写操作具备一致性，避免单靠周期采样充当硬限制。估算字节和服务商计量分别展示，不称为账单精确值。

首次实施使用保守可配置阈值：接近池容量 70% 时预警，85% 时拒绝新环境与扩展性操作，保留修复和删除通道；阈值是平台策略，不是 Supabase 配额。必要时更早停止写入；不能只按数据库空间决定请求和邮件是否可用。超限不自动创建付费项目或升级套餐。

共享池不支持逐应用唤醒 Supabase 计算。UI 区分“应用暂停”“池被服务商暂停”“额度不足”和“上游不可用”，只使用实际支持的恢复流程。冷却重试有次数上限，避免重放写操作。

备份与恢复按应用、环境导出 schema/记录、成员映射和文件清单，恢复到新的命名空间核验后再切换绑定代次。池整体备份恢复可能影响所有应用，不作为单应用撤销按钮。Free 的自动备份能力不能被假定存在，可靠上线前需完成独立备份和恢复演练。

## 配置与迁移

共享模式采用平台维护的服务端池注册表：开发池为启用所需，生产池允许暂未配置，首次发布时要求就绪。每池保存项目标识、PostgreSQL 连接凭证引用、Auth/Storage 服务凭证引用及区域。凭证通过环境或加密存储注入，不写源码和产物。运营侧预先创建池并完成一次性受控初始化，普通应用任务不具有创建 Supabase 项目的能力。

`PIXLOOM_SUPABASE_ACCESS_TOKEN`、组织和创建项目上限不再是共享模式的必填运行配置；它们仅服务旧适配器及独立资源运维。新版限制使用池容量与应用额度，不能把旧 `MAX_PROJECTS` 改名后继续按每应用减二。新配置字段在实现阶段添加至 `.env.example`，本设计不创建空配置冒充已接通。

现有代码须改造的关键位置：

| 位置                                          | 工作                                                                             |
| --------------------------------------------- | -------------------------------------------------------------------------------- |
| `cloud/config.ts`、`store.ts`、`provision.ts` | 新 Provider/池模型，按需环境，移除新模式的 `count + 2` 与远程 ref 应用级唯一约束 |
| `cloud/schema.ts`                             | 独立 schema、角色和 owner RLS；迁移记录按应用环境隔离，清除 `public` 同名表冲突  |
| `cloud/client.ts`、`manifest.ts`、`types.ts`  | Gateway 客户端、v2 配置、可选生产环境、v1 读取兼容                               |
| 新 Cloud runtime Gateway                      | 应用会话、成员、有限查询、文件路径、速率与额度边界                               |
| `cloud/functions.ts`、`test-account.ts`       | Provider 能力检查；共享模式禁止旧函数部署；测试清理不能删除跨应用上游身份        |
| `browser.ts`、预览策略、发布 runner           | 只放行 Cloud runtime；生产延迟分配，精确环境配置和失败保留                       |
| Cloud 面板、API、交付                         | 显示环境和配额，按应用导出，明确共享/独立身份能力和后端依赖                      |

升级不原地删除旧唯一索引后复用 v1 表：旧 SQL 默认写 `public`，部署缓存只按远程项目区分，客户端直连共享 Auth，旧函数验证也没有应用作用域；这些都必须和新协议一起改。已有资源迁移是独立、可恢复操作：冻结写入、导出、转换归属、校验数据/文件/身份、切换绑定；失败回到旧绑定。旧项目的付费资源仅在用户另行明确删除后释放。

## 交付顺序与验收

1. **Provider 与延迟生产环境**：引入版本化绑定和能力检查，保留 legacy/external 行为；启用只需要开发环境，静态应用零分配。兼容旧产物和备份。
2. **共享数据库最小闭环**：管理员注册两个测试池，提供私有 schema/角色、Gateway CRUD、Cloud 身份与成员授权、v2 客户端和迁移。两个应用同名 `todos` 不冲突，刷新重新登录后可读回数据库记录。此阶段新模式不部署任意函数。
3. **存储、发布与配额**：应用对象作用域、生产延迟分配、幂等恢复、容量限流和数据导出。完成备份恢复演练后再接真实业务数据。
4. **隔离函数与弹性 Provider**：受限业务代码运行时、按需临时环境、池扩容与应用迁出。Serverless 数据库适配器须单独验证成本、唤醒和恢复，不在 Supabase 共享池上虚报该能力。

验收必须验证：两个不同应用及同应用两个用户互相越权失败；开发 token 访问生产失败；伪造 app/environment/owner、SQL 标识符、路径穿越和直接访问池 API 无法越权；共享身份未加入应用时访问失败；注销/删除测试账号不伤及其他应用；并发额度预留不超卖；发布失败不切换线上且不复制测试数据；恢复/取消/重启不重复创建命名空间；删除一个应用不删共享项目；新模式全流程没有调用 `/v1/projects` 创建操作。池配置相同地复用于多应用，远程项目数始终为预配置池数。

当前运行实现和独立验收入口见 [共享池说明](cloud-shared.md)。验收使用真实 PostgreSQL、Docker/Vite、Chromium，模型与 Auth/Storage 使用夹具；未连接用户的真实 Supabase 池，不能据此声称已完成真实上游和公网部署验收。首版恢复到新应用空间，保留原应用，不自动切换旧绑定。
